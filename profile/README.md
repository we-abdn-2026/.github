## It usually starts with a question

*Could we build that? What happens if we change this? Why does removing that line fix everything?*

We're a group of Computer Science students at the University of Aberdeen who enjoy following questions a little further than necessary. We want to understand how things work, then have a go at making something of our own.

Sometimes the fun is getting an idea to work. Sometimes it's discovering that the idea was terrible, but the thing we learned along the way was pretty good.

This is where we give those experiments a home.

## Things we'd like to get carried away with

- **Useful little tools** that save five minutes after taking a weekend to build. A questionable investment. An excellent weekend.
- **Games and interactive things** that someone can actually play with. Bonus points if we can explain why they're fun.
- **Questions disguised as projects.** A visualisation, a simulation, a strange prototype: sometimes writing the code is how we work out what we're asking.
- **Ideas outside the syllabus.** The course gives us plenty to think about. We reserve the right to get distracted by something interesting on the way.

These are invitations, not a product roadmap. If an idea doesn't fit neatly into a category, we'd still like to hear it.

## Our relationship with bugs

Complicated, but we're working on it.

A bug is a useful reminder that the computer is running the code we wrote, not the code we confidently described to each other ten minutes ago.

We'd rather share a small, reproducible failure than spend an afternoon pretending everything is fine. “I don't know yet” is a perfectly good place to start. “Fixed it, don't ask how” is where the investigation resumes.

## A few house rules

- **Ask the obvious question.** Someone else probably wants to know too.
- **Make a small version first.** The grand vision can wait until the button works.
- **Review the code, be kind to the person.** Everyone gets to learn; nobody needs a public execution over a variable name.
- **Leave a way back in.** A useful README, a clear commit, a note about the weird bit. Future you has a different workload and absolutely no memory of this clever workaround.
- **Enjoy making things.** Not every repository needs to become a startup.

## Bring a “what if”

Have an idea, found a bug, or want to understand how something works? Open an issue in a relevant repository or join a discussion where one is available. You don't need to arrive with a finished solution.

Code is welcome. So are questions, sketches, tests, clear explanations, and the person who notices we've been solving the wrong problem.
